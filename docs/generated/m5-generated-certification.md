# Generated-artifact certification

This document describes the promotion-grade certification lane that decides
whether a claimed M5 publishable profile may carry the maturity its own
claim-publication object advertises, given the generated-artifact evidence
behind it. The canonical packet is implemented in
[`crates/aureline-generated/src/m5_generated_certification/mod.rs`](../../crates/aureline-generated/src/m5_generated_certification/mod.rs)
and serialized to
[`artifacts/generated/m5-generated-certification-packet.json`](../../artifacts/generated/m5-generated-certification-packet.json).

It sits one level above the per-class
[generated-artifact governance lane](./m5-generated-governance.md): where
governance freezes the seven provenance dimensions every generated artifact
must prove, this lane certifies the five publishable *profiles* — scaffolded
project, notebook output, preview derivative, request artifact, and framework
codegen — and binds each to the real upstream claim-publication object the
product ships.

## Why this exists

M5 ships generated artifacts across many surfaces, and each profile already
has its own claim-publication object that advertises a maturity. Without one
certification lane, those publication claims can outrun the generated-artifact
evidence behind them: a scaffolded project can advertise `stable` while its
canonical-source linkage is partial, or a preview derivative can advertise
`beta` while its regeneration route is gone. This lane closes that gap. It
makes the published claim answerable to four generated-artifact domains and
narrows the claim — or holds promotion — the moment one domain cannot be
proven.

## What each row binds together

Every [`CertificationRow`] binds three things, so the certification can never
float free of what the product publishes or what the governance lane proves:

- the profile's upstream **claim-publication object** (`claim_publication_ref`)
  — the archetype / notebook / preview / request / codegen artifact that
  advertises the maturity;
- the backing generated-artifact **class** (`backing_artifact_class`) the
  governance lane certifies for that profile; and
- the **governance proof packet** (`governance_evidence_ref`) the whole
  certification rests on.

## The certified domains

Every claimed profile must prove four generated-artifact domains. A profile may
not promote at its published maturity unless all four are `current`:

- **`canonical_source_visibility`** — the profile's generated bytes declare and
  link to the canonical source they derive from, so a derived file is never
  presented as authoritative source.
- **`writable_boundary_truth`** — the profile's writable-boundary posture is
  enforced, so a direct edit across a canonical-source boundary is blocked or
  escalated rather than applied silently.
- **`regeneration_path`** — the profile can be rebuilt from its canonical source
  through a declared, reviewable regeneration route.
- **`restore_export_honesty`** — the profile's local-history, restore, and
  support-export packets state exactly what was captured, omitted, or rederived,
  so a restore never implies ordinary full-source history for a derived
  artifact.

Each domain is grounded in a checked-in generated-artifact evidence packet:
`canonical_source_visibility` in the governance proof packet and the
generated-artifact descriptor packet; `writable_boundary_truth` in the
write-boundary and mutation-guardrails packets; `regeneration_path` in the
regeneration-plan packet; and `restore_export_honesty` in the
generated-timeline packet.

## The narrowing engine

Each domain carries an `evidence_state`. One engine —
`certify_profile_outcome` — folds the per-domain evidence into a single
verdict, a certified maturity, and a promotion decision. It is the only place
the downgrade rule lives; the rows, the freshness rules, the drills, and the
fixtures all read it.

| Evidence state | Maturity floor | Promotion |
| --- | --- | --- |
| `current` | none | `promote` |
| `partial` | `beta` | `promote_narrowed` |
| `stale` | `preview` | `promote_narrowed` |
| `missing` | `withdrawn` | `hold` |
| `not_applicable` | none | `promote` |

The certified maturity is the worst (narrowest) of the published claim and
every triggered floor; it can never exceed the published claim. The verdict and
promotion decision follow:

- **`certified` / `promote`** — the certified maturity equals the published
  claim.
- **`narrowed` / `promote_narrowed`** — the certified maturity is below the
  published claim but the profile still promotes at the narrower maturity.
- **`withheld` / `hold`** — a required domain is missing, so the claim is
  withdrawn and promotion is held.

The certification only ever narrows. It never promotes a profile above its
published claim, and a profile absent from the packet is uncertified rather
than implicitly promotable.

## Certified profiles

| Profile | Backing class | Published maturity | Claim-publication object |
| --- | --- | --- | --- |
| `scaffolded_project` | `scaffolded_project` | `stable` | template registry / archetype health bundles certification |
| `notebook_output` | `notebook_output` | `beta` | notebook round-trip / support packet |
| `preview_derivative` | `preview_derivative` | `beta` | publish-preview |
| `request_artifact` | `request_artifact` | `beta` | API collections / request-profile certification |
| `framework_codegen` | `framework_codegen` | `beta` | framework migration / import truth packet |

In the checked-in packet every domain is `current`, so every profile is
`certified` at its published maturity and promotes. A profile's published
maturity is never wider than the governance lane's claim for the backing class.

## No claim outruns its evidence

The marquee guardrail: a green happy-path workflow cannot keep a profile
certified while its writable-boundary or restore/export evidence is stale. The
engine narrows the certified maturity, and a missing domain holds promotion
outright. A profile that cannot prove canonical-source visibility,
writable-boundary truth, a regeneration path, or restore/export honesty is
`hold`, not a silently green row.

## Failure and recovery drills

Each profile carries one failure / recovery drill. A drill injects a failure
into one domain, observes the degraded evidence, watches the claim narrow or
hold, refreshes the evidence, and recovers to `certified`. The degraded outcome
is computed from the same engine the rows use, so a drill can never disagree
with the certification. The drill set covers partial canonical-source
visibility (scaffolded project → beta), stale restore/export honesty (notebook
output → preview), a missing regeneration route (preview derivative → withheld /
hold), a stale writable boundary (request artifact → preview), and a missing
canonical-source linkage (framework codegen → withheld / hold).

## One packet for every surface

Release / shiproom, support export, docs, and help all ingest the same packet
id (`generated.m5_generated_certification.v1`) and preserve the per-row verdict,
certified maturity, promotion decision, and narrowing tokens verbatim:

- `release_shiproom` — holds promotion for any profile whose promotion decision
  is `hold` and publishes the narrowed maturity for any narrowed profile.
- `support_export` — re-exports the verdict, certified maturity, promotion
  decision, and narrowing tokens with no raw generated bytes, credentials, or
  generator payloads.
- `docs` — quotes the certified domains, freshness rules, and per-profile
  verdicts.
- `help` — reuses the same vocabulary in the why-this-certified inspector
  through `certification_copy_line`.
